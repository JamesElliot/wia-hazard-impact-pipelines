# Repository Audit — wia-hazard-layers

**Scope:** full read-only technical audit of the `wia_pipelines` package and its supporting docs, tests, scripts, and tooling, as of branch `review/repo-audit` (commit `282e1fc` plus a substantial uncommitted working tree adding a new hydrodrought/GloFAS-SRI hazard).
**Method:** static reading of source/docs/tests/schemas, execution of the local test/lint/compile suite (no network, no credentials, no pipeline execution), and inspection of ~7.9G of *already-existing* real prior run outputs under `outputs/` as evidence. No files were modified except this report.
**Non-goals:** this audit does not re-derive or challenge hazard science; it reports where implementation, configuration, documentation, schema, and tests agree or disagree, and classifies each disagreement as a software defect, documentation defect, methodological choice, or open methodological question for WIA review.

---

## 1. Executive summary

The repository is a working, well-tested reference implementation. All 137 tests pass, `ruff check` is clean, and `ruff format --check` finds only two minor unformatted files. The core architecture — a shared `RunConfig`/`run_metadata.json` contract, a common `outputs/<ISO3>/<WINDOW>/<hazard>/` layout, and per-hazard pipelines that funnel into shared `core/` primitives — is sound and has scaled cleanly to five hazards, with a sixth (hydrodrought/GloFAS-SRI) currently being integrated in the uncommitted working tree.

That in-flight hydrodrought work is also where this audit's most important finding sits: the new `HAZARD_METHODS` registry entry being added to `core/pipeline.py` currently describes the hydrodrought population rule as "at least 30 consecutive days," but the actual implemented (and separately, correctly documented) rule is "at least 2 consecutive months" (**METHOD-003**). Because this registry string is written verbatim into every run's `run_metadata.json`, every hydrodrought run produced after this lands would carry an incorrect self-description until fixed — this should be corrected before the branch merges.

Beyond that, the recurring pattern across every workstream is **the two newer/less-integrated hazards (earthquake and cyclone) consistently diverge from the pattern the other five hazards share**: they have their own YAML-based config system that partly bypasses the shared `build_hazard_run_context()` (ARCH-007), their own admin-loading and provenance-checksumming code (ARCH-004, PROD-003), and earthquake in particular has an enforcement gap (a denominator-tolerance config key that cyclone enforces but earthquake silently ignores, METHOD-001) and a confirmed performance issue (loading and validating a ~988MB admin file twice per run, PERF-003). None of this is unique to earthquake/cyclone being *bad* — they were added by a different implementation path — but it means "hazard #8" has two contradictory precedents to copy from today.

Test coverage is uneven: SPEI and UTCI — two of the five original, most mature hazards — have **zero pipeline-level test coverage** (TEST-001), and no hazard has a golden numerical-regression test except violence, confirming a gap already flagged (unclosed) in the repo's own `TODO.md`. Documentation is generally strong and unusually self-aware (the hydrodrought implementation plan explicitly documents its own open questions), but has drifted in a few concrete, checkable places — most importantly `CONTRIBUTING.md` still describing the legacy output directory layout (DOC-001), and two docs hardcoding one contributor's local absolute filesystem path (DOC-004).

No critical security issues, no data-loss risks, and no evidence of incorrect *published* numbers were found — the SPEI/UTCI/violence/cyclone default thresholds all match their documentation exactly, and most candidate discrepancies from an initial pre-survey did not hold up under verification (recorded explicitly in §5). The highest-value near-term actions are: (1) fix the hydrodrought registry text before merge, (2) decide and document the config-architecture split for cyclone/earthquake rather than let it read as drift, (3) add pipeline-level tests for SPEI and UTCI, and (4) reconcile `CONTRIBUTING.md` with the current output contract.

**Recommended next action:** fix METHOD-003 (a two-line change) before the current branch is merged, since it is the one finding that would ship an incorrect artifact into every future hydrodrought run.

## 5. Findings register

Severity/confidence are audit judgments, not measurements, unless stated otherwise. "Numerical impact" states whether *applying the recommendation* could change a hazard's published output values — not whether the current bug already does (that's covered in "Consequence").

### Architecture & maintainability (ARCH)

**ARCH-001 — Five near-identical `_cmd_*_postrun` CLI handlers**
Severity: Medium · Confidence: High · Files: `cli.py:259-516` (spei/hydrodrought/utci/flood/violence postrun handlers)
Evidence: the spei and utci handlers differ by exactly 2 lines (parity-module import, qc-subdirectory string) out of ~50.
Consequence: a fix to shared behavior (exit-code semantics, warning-vs-failure policy) must be applied identically in 5 places.
Recommendation: replace with one `_cmd_hazard_postrun(hazard, parity_module)` helper, dispatched via a small table; all 5 `*_parity.py` modules already share an identical `run_checks`/`to_markdown` signature.
Effort: S · Dependencies: none · Numerical impact: none · Verification: existing `test_cli.py` postrun dry-run assertions must still pass unchanged after refactor.

**ARCH-002 — Duplicated CDS download-with-fallback loop (SPEI/UTCI)**
Severity: Medium · Confidence: High · Files: `spei.py:364-442`, `utci.py:272-348`
Evidence: both loop over months, try a "consolidated" dataset request, fall back to "intermediate" on failure, and build near-identical manifest rows — differing only in the CDS variable name and one dict key (`dataset_type` vs `product_type`).
Consequence: the fallback policy is effectively a shared methodology decision duplicated in two places; a fix to one won't reach the other.
Recommendation: extract `core/cds.py: download_month_with_fallback(...)`, parametrized by dataset/variable/dict-key-name.
Effort: M · Dependencies: none · Numerical impact: none (pure refactor, same requests) · Verification: re-run `test_cds.py` + a new unit test asserting identical manifest output before/after.

**ARCH-003 — Duplicated progress-writer math (4-5 copies)**
Severity: Low · Confidence: High · Files: `flood.py:83-114` and `violence.py:67-93` (identical `make_progress_writer`); `spei.py:333-354,530-547` and `utci.py:243-262,432-449` (inline reimplementations of the same elapsed/rate/ETA arithmetic)
Consequence: 4-5 copies of the same status-file schema; a schema change (e.g. new field) requires touching every hazard module.
Recommendation: move `make_progress_writer` to `core/progress.py`; migrate spei/utci's inline closures to call it.
Effort: S · Dependencies: none · Numerical impact: none · Verification: existing progress-file consumers (if any in `batch/`) still parse output unchanged.

**ARCH-004 — "Load admin with zip/layer fallback" reimplementations [PARTIALLY IMPLEMENTED — scope corrected]**
Severity: Medium · Confidence: High · Files: `violence.py:131-139`, `cyclone/pipeline.py:77-85`, `earthquake/pipeline.py:73-82`, `batch/readiness.py:145-151`, vs. the canonical `core/admin.py:24-29 load_admin_layer` (used only by flood/spei/utci)
**Correction (made during batch-6b implementation):** on close reading, `violence.py`'s `_load_admin` and `batch/readiness.py`'s `_read_admin_layer` **are** byte-identical simple loaders (zip-prefix handling + layer-fallback-on-exception, nothing else) and cleanly folded into `core/admin.load_admin_layer` as originally recommended. But `cyclone/pipeline.py`'s and `earthquake/pipeline.py`'s `_load_admin` functions do **substantially more** than load a layer: they also resolve field names (`_actual_column`), filter by ISO3, validate/require an admin-level pcode column, and clean geometries — and the two are not byte-identical to each other either (subtly different exception-handling and empty-result-check ordering). Forcing these into the same "just fold into core.admin.load_admin_layer" fix would have either silently changed their exception semantics or required scope-creeping `load_admin_layer` into a hazard-specific field-resolution function. **These two were deliberately left untouched.**
Consequence: `core/admin.load_admin_layer` is now the single loader for flood/spei/utci/violence/batch-readiness (5 of 7 consumers) with zip-prefix + layer-fallback support. Cyclone/earthquake's `_load_admin` functions remain separate, and — since they genuinely duplicate more logic *between each other* than the audit's original framing captured — are a candidate for their own, separately-scoped future refactor (extracting the shared field-resolution/validation logic between just the two of them), not bundled with this one.
Recommendation: implemented for violence.py/batch-readiness.py/core/admin.py. Cyclone/earthquake's `_load_admin` de-duplication (between each other, not against the canonical loader) is a new, distinct, smaller-scoped finding for a future batch.
Effort: M (as implemented) · Dependencies: none · Numerical impact: none (same loading semantics, just consolidated) · Verification: `test_admin.py` — added `test_load_admin_layer_missing_path_raises_file_not_found`, `test_load_admin_layer_reads_zip_wrapped_source`, `test_load_admin_layer_falls_back_when_named_layer_is_missing`; full suite unchanged otherwise. Status: **fixed** (violence.py + batch/readiness.py portion only).

**ARCH-005 — Duplicated rasterize+`labelled_sum` aggregation block (flood/spei/utci)**
Severity: Low · Confidence: Medium · Files: `flood.py:507-527`, `spei.py:610-628`, `utci.py:505-519`
Recommendation: add `core/aggregation.py: build_admin_id_raster(...)` + `population_totals_by_admin(...)`; migrate the three call sites (check hydrodrought.py for the same pattern when done).
Effort: M · Dependencies: none · Numerical impact: none · Verification: existing per-hazard aggregation tests must produce identical sums before/after.

**ARCH-006 — cyclone/earthquake `config.py` share near-duplicate boilerplate**
Severity: Low · Confidence: High · Files: `cyclone/config.py:13-20,64-70` (`_merge`, `config_hash`) is byte-identical to `earthquake/config.py`'s equivalents.
Recommendation: move `_merge`/`config_hash` into a shared module; keep only hazard-specific `validate_config` local.
Effort: S · Dependencies: none · Numerical impact: none.

**ARCH-007 — Two incompatible config/run-context systems coexist**
Severity: High · Confidence: High · Files: `config.py:49-95` (`RunConfig`, used properly by flood/spei/utci/violence/hydrodrought via `build_hazard_run_context`, `core/pipeline.py:77`) vs. `cyclone/config.py`+`default.yml` and `earthquake/config.py`+`default.yml`, which build a `RunConfig` internally but then **manually reimplement** `build_hazard_run_context`'s body (dir creation, metadata init, schema validation) rather than calling it (`earthquake/pipeline.py:161-162,383-384,437`).
Consequence: a future change to `build_hazard_run_context` (new metadata field, different dir-creation order) silently won't apply to cyclone/earthquake; whoever builds hazard #8 has two contradictory precedents to copy.
Recommendation: either have cyclone/earthquake call `build_hazard_run_context()` directly, or explicitly document the two-tier config architecture (YAML-based hazards need method-specific thresholds `RunConfig` doesn't model) as a deliberate design choice via a short ADR, so it reads as intentional rather than drift.
Effort: M (refactor) or S (document-only) · Dependencies: none · Numerical impact: none if refactored carefully (same metadata fields, same validation) · Verification: `test_earthquake_pipeline.py`/`test_cyclone_pipeline.py` run_metadata assertions unchanged.

**ARCH-008 — Schema validation silently downgraded to "warning" at postrun time by default**
Severity: Medium · Confidence: High · Files: `cli.py:271-282` (and the 4 analogous postrun handlers)
Evidence: a schema-validation failure is caught and recorded as `"status": "warning: ..."`, and only escalates to a real failure if `--strict-metadata-validation` is passed — even though the same schema is a hard `raise` during the actual pipeline run (`config.py:132-139`).
Consequence: a `run_metadata.json` corrupted or hand-edited after the run completes can pass postrun QC silently by default.
Recommendation: default `--strict-metadata-validation` to `True` for postrun commands (opt-out, not opt-in), or rename the status field so "warning" can't be misread as "passed."
Effort: S · Dependencies: ARCH-001 (touch while de-duplicating) · Numerical impact: none (QC-only) · Verification: new test asserting a corrupted metadata file causes postrun to report failure by default.

**ARCH-009 — Repeated argparse boilerplate across `run-*` subcommands**
Severity: Low-Medium · Confidence: High · Files: `cli.py:979-1444 build_parser()` — the same ~10 flags (`--iso3`, `--as-of-date`, `--lookback-months`, `--target-adm-level`, `--output-root`, `--admin-path`, `--admin-layer`, `--iso3-field`, `--worldpop-path`, `--worldpop-dir`, `--dry-run`) re-declared verbatim per hazard subcommand.
Recommendation: factor `_add_common_hazard_args(subparser)`; est. ~100-150 line reduction.
Effort: S · Dependencies: none · Numerical impact: none · Verification: `test_cli.py`'s `build_parser()` dry-run assertions unchanged.

**ARCH-010 — No `logging` module usage anywhere; `print()` substitutes for logging [RE-VERIFIED: NOTHING TO MIGRATE]**
Severity: Medium · Confidence: High · Files: repo-wide (`grep -rln "^import logging\|logging.getLogger" src/` → zero hits); ~30 `print()` sites in `cli.py`, plus scattered ones in `core/mapping.py`, `cyclone/pipeline.py`, `cyclone/footprints.py`, and all four `*_visualize.py` modules.
Consequence: no verbosity control, no timestamps/levels; a library consumer embedding `wia_pipelines` gets uncontrollable stdout rather than a configurable logger. One `warnings.warn` (`flood.py:350`) is inconsistent with the rest.
Recommendation: introduce `logging.getLogger(__name__)` per module (or a `core/logging_config.py` helper); replace diagnostic `print()`s with `logger.info/warning`, leaving the final JSON-payload `print()`s in `cli.py` (the intended CLI contract) alone.
Effort: M · Dependencies: none · Numerical impact: none.
**Status: re-verified against the current codebase; there is nothing left to migrate.** A word-boundary-safe re-grep (`[^a-zA-Z_.]print(`, since a plain `grep -c print` matches the substring "print" inside "footprint"/"footprints" too) found **zero** real `print()` calls in `core/mapping.py`, `cyclone/pipeline.py`, `cyclone/footprints.py`, or any of the four `*_visualize.py` modules this finding named — every match in those files was `footprint`/`footprints` as a function name, docstring word, or variable name, not a `print()` call. It's not established whether these were ever real print() calls that got cleaned up in an earlier batch of this session, or whether the original audit's own grep had this same substring false-positive from the start; either way, there's nothing to fix in these 7 files today. `cli.py`'s 31 `print()` calls are all real, but every one of them is exactly the JSON-payload/human-readable CLI output contract this finding's own recommendation says to leave alone. So the only fact that still holds is "no `import logging` anywhere in `src/`" — true, but with zero diagnostic `print()` output anywhere left to replace, adding `logging.getLogger()` scaffolding now would be unused infrastructure with no current call sites, not an actual fix. Not implemented, on the same "don't build for a hypothetical future requirement" grounds this audit itself would flag elsewhere. Risk: **medium** — vectorizing a distribution fit must exactly preserve the existing gamma-vs-empirical fallback branching (`hydrodrought.py:594-598`); a naive vectorization could silently reclassify which cells use which method, changing SRI values. **Status: benchmarked as this entry itself prescribed, then deferred — not worth the risk.** Timed `fit_baseline_distribution()` in isolation (30-year monthly-accumulated baseline, 360 samples/cell, the realistic case): ~0.43ms/cell. Extrapolated to grid size: island-scale (50×50) ≈1.1s total; a large country at GloFAS resolution (300×300) ≈39s; even an unrealistically large 500×500 grid ≈108s (~1.8 minutes). Since hydrodrought's overall runtime is already documented elsewhere as a multi-hour operation (EWDS downloads dominate), a loop costing at most ~2 minutes even at the largest plausible scale is not a meaningful bottleneck — and the alternative (a hand-rolled vectorized gamma MLE, since scipy has no batched fit across independent samples) carries a real, this-entry-acknowledged risk of silently reclassifying which cells use gamma vs. the empirical fallback, changing published SRI values for a real hazard indicator. **PERF-010 — Earthquake ShakeMap fetches are sequential with no retry/backoff [FIXED]**
Severity: Medium · Confidence: High (confirmed code path; slowdown magnitude **suspected**, no real event counts checked) · Files: `earthquake/pipeline.py:204-296` iterates the USGS catalog sequentially, one detail-fetch + one grid.xml fetch per event, no concurrency; `earthquake/client.py:38-41 fetch_bytes` is a bare `urllib.request.urlopen` with a timeout but **no retry/backoff** — any transient USGS failure on any single event aborts the entire run. Risk: low for retry/backoff (pure robustness). Low-medium for concurrency — result is order-independent by construction, but event-row ordering (currently relies on catalog iteration order) would need explicit re-sorting after a concurrent merge to keep QC-table row order stable/reproducible.

**Status: fixed, after an initial deferral.** First assessed and deferred (see git history) because the literal recommendation — wrap `client.fetch_bytes` — conflicts with `test_earthquake_client.py::test_download_cached_recovers_after_a_failed_attempt`, which deliberately asserts a failing first call raises rather than silently retrying into success. Asked the user where retry should live rather than either rewriting that test's contract or skipping retry entirely; they chose a call-site wrapper. New tests: four for `_fetch_with_retry` (succeeds without retry, recovers after transient failures, exhausts retries and re-raises, does not retry non-transport errors) and one multi-event `run_pipeline` test with three synthetic USGS events in a deliberately mixed excluded/included/excluded order, asserting `event_rows` comes back in exact catalog order. Full suite: 222 passed (up from 217), `ruff check`/`ruff format --check`/`compileall` clean.

## 6. Performance assessment

**Confirmed bottlenecks** (algorithm read directly, mechanism is clear from code):
PERF-003 (earthquake double admin-load), PERF-004 (repeated full-file checksums), PERF-005 (write-then-reread), PERF-006 (earthquake/violence aggregation scaling with admin-polygon count vs. flood/spei/utci/hydrodrought's flat `labelled_sum`), PERF-007 (unnecessary float64 cast, measured against real file sizes), PERF-009 (cyclone's un-reused spatial index), PERF-010 (sequential earthquake fetches, no retry), PERF-011 (resume doesn't verify artifacts), PERF-012 (fully sequential batch execution).

**Suspected but unmeasured** (mechanism plausible, magnitude not established — flagged explicitly rather than asserted):
PERF-001's real-world redundant-download frequency, PERF-002's actual duplicate-fetch rate, PERF-006's real wall-clock impact at typical admin-polygon counts, PERF-007's actual peak-memory/OOM risk for a large country (no large-country run was executed — VCT/GRD's existing outputs are 1,500-4,000× smaller by pixel count than NGA/COD, so nothing in the existing artifacts would reveal this), PERF-008's real slowdown magnitude (depends on `fit_baseline_distribution`'s per-call cost, not profiled), PERF-010's real fetch-count-driven slowdown (no country with many small earthquakes was checked against existing QC outputs), PERF-012's achievable parallelism (bounded by unverified CDS/EWDS concurrency limits).

**One positive control worth naming explicitly:** `core/rivers.py`'s nearest-reach pixel assignment (new, untracked code supporting hydrodrought) correctly uses `scipy.ndimage.distance_transform_edt` — a genuine vectorized distance transform, not a naive per-pixel or O(n·m) brute-force search — and the module's own docstring explains this was a deliberate choice. `flood_recurrence.py`'s windowed/blocked processing was likewise found clean. Not every new module has a performance problem.

**Recommended benchmark dataset:** use the already-present real WorldPop files spanning three orders of magnitude (GRD/VCT ~1,500 pixels² through NGA/COD ~2×10^8 pixels²) as the standard small/medium/large fixture set for any future timing work — no new data needs to be fetched.

## 8. Test and validation plan

Recommended five-tier framework, concrete to this repository (not generic advice):

1. **Software tests** (what most of the suite already is — unit/component level). Close the gaps in TEST-001 through TEST-009 above. Introduce a `conftest.py` with two shared fixture factories — `make_admin_gpkg(tmp_path, iso3, n_features, adm_level)` and `make_worldpop_tif(tmp_path, shape, value, nodata, transform)` — to remove the ~150-200 lines of near-identical inline fixture-building currently duplicated across `test_hazard_spei.py`, `test_hazard_hydrodrought.py`, `test_hazard_violence.py`, `test_cyclone_pipeline.py`, and `test_earthquake_pipeline.py`. This directly makes it cheaper to add the CRS-mismatch (TEST-003) and negative-path (TEST-002, TEST-008) tests recommended above.

2. **Numerical regression tests** (golden cases — currently only violence has one). For each of SPEI, UTCI, flood, hydrodrought, earthquake: one minimal synthetic run (small raster + 1-2 admin polygons, following the pattern violence/cyclone tests already use), hand-computed expected `pop_affected`/`pct_affected`/threshold-crossing values, locked with `assertAlmostEqual`. This is exactly what `TODO.md` already calls for under SPEI/UTCI/flood (unchecked) — treat closing those three, plus adding equivalent cases for hydrodrought and earthquake, as the concrete tier-2 backlog.

3. **Dataset-integration tests** (real external data shape — currently mostly absent). Mark `@pytest.mark.slow`/skip-by-default (the `slow`/`integration` pytest markers are already declared in `pyproject.toml` but currently unused by any test — a quick win in itself). Exercise a small real clip of each dataset: a 1-admin1 clip of a real WorldPop tile (several already sit in `data/population/`), one real CDS SPEI3/UTCI NetCDF month, a real IBTrACS CSV excerpt, a recorded (cassette-style) GDACS/USGS API response. This is also the right tier for the network-failure tests in TEST-008, using recorded cassettes rather than live APIs to simulate timeouts/bad responses.

4. **Methodological validation against independently-calculated examples.** For each hazard's headline number, pick one real, already-published country/event case with an independently known or publicly reported affected-population figure (e.g. a historical cyclone with a known IFRC/OCHA-reported figure) and check the pipeline's output falls in a plausible range. This validates the *method*, not just internal consistency, and should live outside `tests/` (e.g. `docs/validation/`, as a notebook or script) since real-world reference numbers carry their own uncertainty and shouldn't be pytest hard-assertions.

5. **Country-level plausibility checks** (sanity gates for unattended batch runs). Extend the existing `*_parity.py` post-run checks — which currently only have PASS-case tests (`test_flood_parity.py`, `test_violence_parity.py` both test only `test_run_checks_passes_on_minimal_valid_run`) — to also have a FAIL-case test, and to flag `pct_affected` outside [0,100], population totals diverging from a trusted country total beyond tolerance (formalizing what PROD-001/METHOD-001's denominator checks are already trying to guard), and hazard-specific sanity bounds (MMI-exposed population ≤ country population, flood-days ≤ days in window).
